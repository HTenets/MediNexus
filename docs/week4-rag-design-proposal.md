## 一、整体架构概览

```ascii
用户查询（症状 + 上下文）
         │
         ▼
    Query Router ──→ 并行召回三路知识源
         │
         ├──→ 源A: 临床病例库 ──→ chunking A ──→ vector store A
         ├──→ 源B: 医学理论库 ──→ chunking B ──→ vector store B
         └──→ 源C: 最新论文库 ──→ chunking C ──→ vector store C
                                          │
                                          ▼
                              初始召回结果 (Top-K per source)
                                          │
                                          ▼
                 ┌─────────────────────────────────────┐
                 │      三路融合 & 重排序层               │
                 │  ① 置信度加权                          │
                 │  ② Z-score 跨源标准化                  │
                 │  ③ RRF 融合 → 最终排序                 │
                 └─────────────────────────────────────┘
                                          │
                                          ▼
                             知识图谱增强 (可选层)
                     ┌─ 症状-疾病关系图谱 ─┐
                     │  疾病-药物关联      │
                     └── 多跳推理扩展 ────┘
                                          │
                                          ▼
                               LLM 生成最终回答
```

## 二、三路知识源设计

### 源A: 临床病例库 (Confidence: 0.8 - 高)

| 维度 | 方案 |
|------|------|
| **数据来源** | 公开病例集 (NEJM Case Records、中国临床案例库)、本项目积累的问诊记录 |
| **权威性** | 高 — 真实临床实践验证 |
| **置信度** | `weight_A = 0.8` |
| **适用场景** | 常见病诊断、典型表现匹配 |

**论文参考:** MECR-RAG (Wong & Wong 2025) 使用 3000 例真实 triage 病例 + 指南双源 RAG，QWK=0.902。验证了临床病例在 RAG 中的高价值。

### 源B: 医学理论库 (Confidence: 0.5 - 中)

| 维度 | 方案 |
|------|------|
| **数据来源** | 教科书、临床指南、专家共识、诊疗规范 |
| **权威性** | 中 — 理论框架完整，但可能与真实病例有偏差 |
| **置信度** | `weight_B = 0.5` |
| **适用场景** | 鉴别诊断框架、标准治疗方案 |

### 源C: 最新论文库 (Confidence: 0.3 - 低)

| 维度 | 方案 |
|------|------|
| **数据来源** | PubMed/arXiv 最新研究、临床试验报告 |
| **权威性** | 低 — 前沿，但可能未经充分临床验证 |
| **置信度** | `weight_C = 0.3` |
| **适用场景** | 疑难杂症、罕见病、探索性治疗思路 |

**激活条件:** 当源A+源B的检索置信度低于阈值（如 max_score < 0.5）时，自动激活源C。

## 三、差异化分块策略

论文调研明确结论: **"One strategy can't fit all"** (Redis RAG Chunking Guide 2025)。

### 分块策略对比

| 策略 | 源A(病例) | 源B(理论) | 源C(论文) |
|------|-----------|-----------|----------|
| **分块方法** | 语义边界分割 | 层次化(父-子) | 递归分割 |
| **Chunk 大小** | 256-512 tokens | 512-1024 tokens (父) / 128-256 (子) | 512 tokens |
| **关键约束** | 保持病例完整性(主诉+检查+诊断+治疗) | 保留标题层级(## → ### 映射) | 保留摘要+结论(核心信息不丢失) |
| **Metadata** | 病例ID, 疾病, 科室, 年份 | 来源指南, 证据等级(A/B/C), 章节路径 | DOI, 年份, 期刊, 作者 |
| **重叠** | 10% | 20% (父子跨层) | 10% |

### 论文依据

| 论文 | 主要结论 | 对本方案的指导 |
|------|---------|--------------|
| **MultiDocFusion** (2026) | DFS遍历文档树构建连贯chunk，提升 8-15% 检索精度 | 源B(理论)采用层次化分块，保留章节树 |
| **TopoChunker** (2026) | 结构化中间表示(SIR) + 检查器路由，Recall@3=83.26% | 分块策略按文档类型动态选择 |
| **Adaptive Chunking** (2026) | 5 维指标自动选择分块策略，准确率 62%→72% | 三种源使用不同策略，而非一刀切 |

## 四、三路融合与置信度加权方案

这是核心设计。参考 **HF-RAG (CIKM 2025)** 提出的 **层次化融合** 框架:

### 步骤 1: 源内融合 (Intra-source Fusion)

每个知识源内部可能使用多个检索器（sparse + dense），通过 **RRF (Reciprocal Rank Fusion)** 合并:

```
score_A(doc) = 1 / (k + rank_BM25(doc)) + 1 / (k + rank_dense(doc))
```

- `k = 60` (HF-RAG 推荐值)

### 步骤 2: 置信度加权 (Confidence Weighting)

三种源各自有基础置信度，还可根据查询相关性动态调整:

```
final_score(doc) = w_source × score_A(doc)

其中 w_source = base_weight × query_source_relevance
               - 源A: base = 0.8
               - 源B: base = 0.5
               - 源C: base = 0.3
```

### 步骤 3: 跨源标准化 + 融合

由于三种源的得分分布不可比，参考 **HF-RAG 的 Z-score 标准化**:

```
z_score(doc) = (score(doc) - μ_source) / σ_source
final_score = w_A × z_A + w_B × z_B + w_C × z_C
```

### 步骤 4: 动态权重调整（可选增强）

参考 **Entropy-Based Dynamic Hybrid Retrieval (ICML 2025)**，用 **Shannon 熵** 作为检索置信度代理:

```
若 源A 的召回结果熵低（高确定性）→ w_A 增大
若 源A 的召回结果熵高（低确定性）→ w_A 减小，源C 权重增大
```

## 五、知识图谱增强方案

### 现有开源方案调研结论

**不要重复造轮子。** 以下已有成熟方案可直接利用或参考:

| 项目 | 规模 | 语言 | 说明 |
|------|------|------|------|
| **QASystemOnMedicalGraph** (刘焕勇) | 44k 实体 / 300k 关系 | 中文 | 疾病为中心的 KG，Neo4j，4.2k stars |
| **OpenKG DiseaseKG** | 44k 实体 / 312k 关系 | 中文 | 开源数据集，疾病-症状-药品-科室 |
| **SNOMED CT-powered KG** (Ho et al. 2025) | 标准化本体 | 英文/多语言 | Neo4j + SNOMED CT，可映射中文 |
| **KI-DDI GAT** (2024) | 症状-疾病图 + GAT | 中英文 | Graph Attention Network 增强诊断 |

### 知识图谱在 RAG 中的作用

```
症状描述 "头痛、发热、呕吐"
       │
       ▼
KG Query ──→ 症状节点 "头痛" ──→ 关联疾病 ["感冒","脑膜炎","偏头痛"]
       │          "发热"  ──→ 关联疾病 ["感冒","肺炎","流感"]
       │          "呕吐"  ──→ 关联疾病 ["脑膜炎","胃肠炎"]
       │
       ▼
Graph Walk ──→ 多跳推理:
  头痛 → 脑膜炎 → 需紧急处理(颈强直+发热+头痛=三联征)
       │
       ▼
注入 LLM Context ──→ 提升诊断全面性，减少漏诊
```

### 推荐方案: 混合架构

```
RAG 向量检索 (三路)  ←→  知识图谱 (Neo4j)   ←→  LLM 诊断
       │                       │                      │
  语义相似度匹配          结构化关系查询           推理生成
  召回内容片段            发现隐藏关联            综合回答
```

**关键洞察:** 不将 KG 作为独立推理引擎，而是作为 **RAG 的增强组件**:
1. 用户症状 → 向量检索三路知识 → 初始上下文
2. 同时 KG 查询症状关联疾病 → 扩展示意 list
3. KG 结果作为额外 context 注入 LLM
4. LLM 综合向量+知识图谱信息做最终诊断

## 七、实施路径建议

```
Phase 1 (W4 前半): 三路知识库构建
  ├── 数据采集: 收集病例/理论/论文 原始数据
  ├── 分块 pipeline: 为三种源配置不同 chunker
  ├── 向量化 + 写入 Qdrant
  └── 单元测试: 检索召回测试

Phase 2 (W4 中): 融合 & 重排序层
  ├── 实现 RRF 融合 (源内)
  ├── 实现 Z-score 标准化 + 置信度加权 (源间)
  └── 集成重排序模型 (bge-reranker-v2)

Phase 3 (W4 后): 知识图谱集成
  ├── 部署 Neo4j
  ├── 导入 OpenKG DiseaseKG 数据
  ├── 实现症状→疾病→药物 查询接口
  └── 集成到 RAG 流程

Phase 4 (后续): Review Agent + 端到端联调
  └── 用 RAG 结果增强 Review Agent 审查
```

## 八、决策记录 (2026-06-01 定版)

### A. 置信度权重 ✅ 已定
**决定:** `w_A(病例)=0.8`、`w_B(理论)=0.6`、`w_C(论文)=0.3`
- 先固定值，后续通过消融实验调整
- 暂不实现动态权重，保留接口

### B. 知识图谱深度 ✅ 已定
**决定:** 轻量级，只做症状→疾病一跳映射，辅助 RAG 召回
- 不实现多跳推理、不构建全链路
- 方案: 利用 OpenKG DiseaseKG 或 QASystemOnMedicalGraph 的数据，部署 Neo4j 做一跳查询

### C. 数据来源 ✅ 已定
**决定:** 从权威网站/论文数据库爬取
- 病例: NEJM Case Records、中国临床案例库、PubMed Central
- 理论: uptodate、中华医学会指南、公开教科书
- 论文: PubMed API / arXiv API 获取摘要索引
- 具体实现: 先爬取一批种子数据，后续持续扩展

### D. Review Agent 定位 ✅ 已定
**决定:** Review Agent 独立查询数据库来验证 Doctor 输出
- Review Agent 不共享 Doctor 的 RAG 结果
- 独立发起查询，对比验证诊断/处方
- 架构: 两个 RAG 实例（Doctor RAG + Review RAG）共享同一个向量库，但查询逻辑独立

### E. 降级策略 ✅ 已定
**决定:** 提供 BM25 全文搜索降级
- Ollama/BYO Key 不可用 → 向量检索降级到 BM25
- 实行: 每个知识源同时维护向量索引 + BM25 倒排索引
- 降级判定: Qdrant 不可用或 embedding 服务不可用时自动切换
