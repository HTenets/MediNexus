## 【正文】

### 1. Demo 简介

**是什么：** MediNexus 是一个开源的多智能体 AI 医疗问诊 Web 系统（网站 + API），用户输入症状，系统通过 **分诊 → 专科诊断 → 方案审查 → 随访跟踪** 的完整 Agent 流水线，输出结构化、可溯源的医疗参考建议。

**面向谁：**
- **普通患者（核心用户）：** 有轻微不适但不确定是否该去医院的用户
- **基层医疗工作者：** 需要辅助诊断参考的社区医生、乡村医生
- **上班族 / 慢性病患者：** 日常健康监测、久坐提醒、复诊期间的病情跟踪

**主要功能：**

| 功能 | 说明 |
|------|------|
| **AI 智能分诊导诊** | 输入症状 → Triage Agent 多轮对话收集关键信息 → 判断紧急程度（routine / urgent / emergency）→ 推荐对应科室，避免挂错号 |
| **多智能体协作诊断** | Doctor Agent 搭载专科 Skill（皮肤科/耳鼻喉科/内科/心理健康等），结合三路 RAG 知识库（临床病例 + 医学理论 + 前沿论文）给出诊断建议；Review Agent 独立审核方案，检查药物相互作用和禁忌症，所有输出带证据等级标记（A/B/C） |
| **个人健康管理 + 随访跟踪** | Follow-up Agent 根据诊断结果生成随访计划，支持慢性病监测和健康数据追踪 |

### 2. Demo 创作思路

**灵感来源：**

我来自四线小城市，身边很多亲戚朋友遇到大病往往需要去省会或一线城市就医，劳民伤财。同时作为一名程序员，日常久坐和熬夜也在慢慢损耗健康。随着 LLM 的快速发展，我在想：如果把医学理论知识、临床案例、前沿论文等数据作为知识库喂给 Agent，它能否成长为一个全能的个人健康管家 + 医疗问诊专家？这让我看到了很多可能性。

同时，开源社区有很多优秀的 LLM 项目，但没有一个真正面向医疗问诊场景、且具备完整 Agent 协作流程的开源方案。我决定做一个——既能为患者提供参考级医疗建议，又能作为个人健康监测管家，让每个人都能享受到更好的医疗问诊条件。

**想解决的问题：**
- 搜索引擎查病结果混杂广告，难以分辨可靠信息
- 现有 AI 问诊产品多为商业闭源，回答缺乏证据溯源和审核机制
- 患者不知道症状该挂什么科，常挂错号浪费时间和金钱
- 医疗 AI 领域被大公司垄断，缺乏开源方案让开发者参与改进

**为什么做这个方向：**

作为一名研二在校生，我希望通过这个项目边学边做，提升对 LLM 和 Agent 框架的理解，为秋招打基础。选择"社会服务"赛道，是因为医疗问诊本质上是一种公共服务——它不应该被商业公司垄断，应该让每个人都能免费获得参考级的医疗建议。项目所有代码在 GitHub 开源，任何人都可以审查、改进、部署自己的实例。

#### 4.6 开发心得与踩坑经验

**1. LLM 输出格式不可靠**

即使 Prompt 中明确要求 JSON 格式，LLM 仍可能输出非标准格式（比如多输出一句解释性文字）。最终采用了"JSON Schema 约束 + Pydantic 验证 + 解析失败重试 + 关键词兜底"的多层防御策略，确保系统鲁棒性。这个经验来自 `6a16ede835be1708a3a1d3db` 和 `6a32c1517afcb7535d4231a4` 这两个 Session 中与 TRAE 的反复讨论。

**2. 设计稿到代码的精确还原**

TRAE 的 Code 模式非常擅长将设计稿中的布局、颜色、间距精确还原到代码中。关键技巧是：把设计稿的文件路径明确告诉 TRAE，让它逐页对照实现，而不是一次性给所有页面。每完成一个页面，让 TRAE 做一次自检。

**3. Agent 协作的编排复杂度**

5 个 Agent 之间的状态传递和错误处理是最大的挑战。通过 LangGraph 的 StateGraph 管理全局状态，每个 Agent 只读写自己关心的字段，降低耦合。TRAE 在理解 LangGraph 的 State 机制上帮了大忙。

**4. 知识库分块策略的选择**

临床病例适合用 SemanticChunker（按段落分块），医学理论适合用 HierarchicalChunker（父子块结构）。不同场景需要不同的分块策略，没有银弹。这是在 TRAE 中逐行分析 `chunker.py` 代码后得出的结论。

## 附：你是怎么用 TRAE 把 Demo 做出来的

### 从"去医院看病"这件小事说起

去医院看病的流程，普通人可能都经历过，不管大病小病：挂号（导医）、问诊、专家会诊、开药、后期随访。我对这些环节太熟悉了，所以一开始脑子里就有一个很自然的映射——**把每个环节看成一个独立的 Agent，患者就是在和不同的 Agent 交互**。分诊护士是一个 Agent，专科医生是另一个 Agent，药房审核是第三个 Agent。

但问题来了：我是研二学生，会写代码，但从没做过多智能体系统，也没用过 LangGraph，前端框架也只是略懂。这个想法在脑子里转了很久，一直不知道怎么落地。

### 第一步：把脑子里的想法"讲"给 TRAE 听

我的方式很笨——就像跟人聊天一样，一句一句说。

我先跟 TRAE 说：「我想做一个医疗问诊系统，核心是多个 Agent 协作。第一个 Agent 是分诊护士，负责收集患者症状、判断紧急程度、推荐科室。你帮我设计一下这个 Agent 的基类。」

TRAE 没有直接甩代码，而是先问我：「你的 Agent 之间怎么传递状态？是用共享内存还是消息传递？」

这个问题把我问住了。我之前根本没想过。然后 TRAE 给我分析了两种方案的优劣，最后建议用 **HandoverManifest（交接清单）** 的模式——每个 Agent 处理完后输出一个结构化的清单，下一个 Agent 拿着清单继续。这就像医院里医生看完病写病历，下一个医生先看病历一样自然。

那一刻我觉得：**原来架构设计可以这么聊出来**。不是我先想好全部细节再写代码，而是边聊边成型。

### 第二步：「原来这么简单」的瞬间

最让我震撼的是 **Agent 自动注册** 这个功能。

我一开始跟 TRAE 说：「我想让系统启动时自动发现所有 Agent，不用手动 import。」我以为这需要很复杂的插件机制。结果 TRAE 给我用了一个**装饰器模式**——在基类上加一个注册中心，每个 Agent 类定义时自动注册自己。核心代码就十几行：

```python
# 简化版示意
class AgentRegistry:
    _agents = {}
    
    @classmethod
    def register(cls, name):
        def decorator(agent_class):
            cls._agents[name] = agent_class
            return agent_class
        return decorator

@AgentRegistry.register("triage")
class TriageAgent(BaseAgent):
    ...
```

写完后我愣了一下——**这就是插件系统？** 我之前以为需要搞什么动态加载、importlib、entry_points，结果一个装饰器就搞定了。TRAE 还帮我理解了为什么这样可行：Python 的类定义本身就是执行过程，装饰器在类定义时触发注册，没有任何魔法。

这种「原来这么简单」的感觉，后面还出现过好几次：
- RAG 知识库分块，我以为要写复杂的 NLP 逻辑，结果 TRAE 帮我用 SemanticChunker 按段落分块，几十行代码
- 前端从 HTML 迁移到 Next.js，我以为要重写全部逻辑，结果 TRAE 逐页迁移，每页改完立刻能跑

### 第三步：TRAE 帮我跨过的坎

**最大的坎是 LLM 输出格式不稳定。**

我的分诊 Agent 需要 LLM 返回结构化的 JSON，包含 `urgency`（紧急程度）、`department`（推荐科室）、`reason`（判断依据）等字段。但 LLM 经常不听话——有时候多输出一句解释性文字，有时候字段名拼错，有时候直接返回 markdown 格式。

我一开始的思路是：写更详细的 Prompt，把要求说得更清楚。结果**改了十几次 Prompt，失败率还是 20% 左右**。

然后我跟 TRAE 说这个问题，TRAE 的回答让我醍醐灌顶：

> 「Prompt 约束只是第一层防线。你需要多层防御：JSON Schema 约束 → Pydantic 验证 → 解析失败重试 → 关键词兜底。」

具体来说：
1. **第一层**：Prompt 里要求 JSON 格式（已经做了）
2. **第二层**：用 Pydantic Model 定义 schema，LLM 输出后用 `model_validate` 校验，字段缺失直接报错
3. **第三层**：校验失败后，自动重试一次，附带错误提示让 LLM 修正
4. **第四层**：如果重试还失败，降级到关键词匹配——从原始文本里提取"急诊""皮肤科"等关键词，走规则引擎兜底

这个方案实施后，**分诊成功率从 80% 提升到 99%+**。这个坎我原本以为搞不定，因为 LLM 的随机性感觉不可控。但 TRAE 帮我意识到：**不要试图消除随机性，而是建立容错机制**。这个思维转变对我来说比代码本身更有价值。

### 第四步：前后端联调的"绝望时刻"

项目后期，前端 Next.js 和后端 FastAPI 联调时遇到了一个诡异的问题：登录接口返回 503。

我查了半天，最后跟 TRAE 一起排查，发现是环境变量 `DEMO_MODE` 默认设成了 `false`，导致后端在演示模式下也不接受登录。TRAE 帮我改了默认值，然后生成了一键修复脚本，30 秒解决问题。

这种时刻让我感受到：**TRAE 不只是写代码的工具，更是一个能陪你 debug 的伙伴**。你把报错贴给它，它不只是说"改成什么"，而是帮你理解"为什么错"。

### 总结：我和 TRAE 的配合方式

回顾整个项目，我和 TRAE 的配合模式大概是：

1. **我负责想"做什么"和"为什么"**——医疗问诊的场景、Agent 协作的逻辑、用户体验的细节
2. **TRAE 负责"怎么做"**——架构选型、代码实现、bug 排查
3. **我们一起讨论"做得对不对"**——TRAE 会反问我设计决策，我质疑它的方案，最终达成共识

不是我把需求文档甩给它让它写，也不是它说什么我照抄。**是对话，是协作，是两个人（一个人和一台机器）在共同思考**。

如果你问我 TRAE 最让我惊喜的是什么？不是代码能力，而是**它会问对的问题**。当我描述完需求，它不会急着写代码，而是先问：「你这个场景下，Agent 之间怎么传递状态？」「LLM 输出不稳定怎么办？」「你的知识库用什么分块策略？」

这些问题，才是真正帮我跨过坎的东西。
