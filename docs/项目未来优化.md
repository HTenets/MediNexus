## 一、本次发现的问题（文档 vs 代码落差）

`医枢Agent.md` 第 6.3 节描述的三步融合（RRF 源内融合 → Z-score 跨源 → 置信度加权）是**理想化设计**，当前代码实际跑的是简化版。核心落差：

| # | 文档描述 | 代码实际（`backend/knowledge/retriever.py`） | 影响 |
|---|---|---|---|
| 1 | RRF 源内融合多路检索器 | 每库只有一路向量检索，RRF 是**空操作**（代码注释自认 "RRF is just ranking"） | 融合算法名不副实，无实际融合能力 |
| 2 | Z-score 归一化 RRF 分数 | Z-score 归一化的是**原始 cosine 分数** | 与文档语义不符，需要澄清两种口径 |
| 3 | BM25 是检索通道之一 | BM25 仅作**降级路径**（Qdrant 挂了才启用） | BM25 的能力没被充分利用 |
| 4 | 知识图谱参与融合打分 | 图谱结果被**硬编码** `z_score=1.0`、插到位置 0（`rag.py`） | 图谱永远压过所有检索结果，破坏打分一致性 |

### 当前"半吊子"实现清单（具体代码位置）

1. **RRF 空操作**：[retriever.py](../backend/knowledge/retriever.py#L96-L99)
   ```python
   # Step 3: RRF intra-source fusion (for sources with multiple retrievers)
   # For now, each source uses a single retriever, so RRF is just ranking
   for stype in source_chunks:
       source_chunks[stype].sort(key=lambda c: c.score, reverse=True)
   ```
   设计上是给"每库多路召回"预留的位置，但当前没有多路可融，退化成普通排序。

2. **Z-score 套在原始分数上**：[retriever.py](../backend/knowledge/retriever.py#L157-L182)
   - 对"通过 similarity_threshold(0.3) 的那一小撮候选"算 μ/σ，样本极小且带偏（只统计了 top 分数）；
   - 单结果时退回 `score/max_score` 的伪 Z，规则不统一；
   - 三个库用同一 embedder + 同一 COSINE 度量（[vector_store.py](../backend/knowledge/vector_store.py#L42-L45)），原始分数尺度本就可比，Z-score 是否必要存在争议（见下文"融合设计"）。

3. **知识图谱硬插**：[rag.py](../backend/knowledge/rag.py#L116-L138)
   ```python
   graph_chunk.z_score = 1.0
   graph_chunk.final_score = 0.7 * graph_chunk.confidence_weight
   result.chunks.insert(0, graph_chunk)   # 永远插在位置 0
   ```
   图谱结果既不参与融合打分，又永远排在第一位，等于"图谱赢了所有检索结果"。

4. **每库单一检索通道**：[source.py](../backend/knowledge/source.py#L32-L35)
   三个 collection 都用纯向量检索 + 同一个 `similarity_threshold=0.3`，没有针对各知识库特性（病例要精确、理论要术语混合、论文要时效）做差异化检索。

5. **知识库数据量极小**：文档多处提到知识库只有 3 条 seed 数据，检索质量评测（Recall@10/MRR）尚未用真实评测集跑过（见 21.5 节说明）。

## 二、融合设计的两种干净方案（二选一）

**核心辨析**：RRF 之后为什么还要 Z-score？

- **第一层（理论）**：RRF 只在"每库多路对称通道"下才会产生真正可比的无量纲分数。若每库通道数相同，RRF 分数天然可比，**直接加权即可，Z-score 是多余的**。"置信度不同所以要标准化"是概念混淆——置信度应由权重表达（信任度），Z-score 只负责尺度对齐（可比性）。
- **第二层（代码现实）**：当前 RRF 是空操作，跨源组合的是原始 cosine 分数，此时 Z-score 有存在必要（拉平不同 collection 的分数分布）。

**方案 A（对称通道，推荐先做）**：每库用相同通道组合（如都做 dense + BM25）→ RRF 分数可比 → 直接乘置信度权重，去掉 Z-score。简单、正确、易解释。

**方案 B（非对称通道）**：每库通道数不同（如病例 3 路、理论 2 路）→ 通道多的库 RRF 分数天花板更高 → 需 Z-score（或 min-max）先对齐动态范围，再乘置信度权重。

**随方案一并修复**：知识图谱从"硬插"重构为"参与融合打分"——作为病例库的附加通道（或独立源），按真实 score 走 RRF/Z-score/加权流程。

## 三、未来优化方向（按流水线分阶段 + 优先级）

### ① 知识库划分
- **P0｜增加第 4 路：药品/处方知识库**（相互作用/禁忌症/剂量）
  - 理由：项目强调"8 维处方审查 + 14 组药物相互作用规则"，但规则是死代码；Review Agent 的 RAG 只有病例/理论/论文，没有专门药品知识——结构缺口。
  - 设计：药品库独立成源（或单独服务 Review Agent），规则引擎做硬兜底、RAG 做泛化补充。
- **P2｜置信度动态化**：论文被验证/引用后可上调，病例加时效衰减，让 0.8/0.6/0.3 从常量变成可更新状态。
- **P2｜入库质量门禁 + 去重**：当前数据治理空白，需建入库校验（字段完整性、医学实体合法性、重复检测）。

### ② 检索方式（每库定向多路召回）
用 RRF 在源内融合各路，让 RRF 名副其实：

| 知识源 | 通道 1 | 通道 2 | 通道 3 |
|---|---|---|---|
| 病例库(0.8) | Dense 向量 | 症状关键词精确匹配（复用症状词典/图谱） | 结构化元数据过滤（疾病分类/年龄/性别） |
| 理论库(0.6) | Dense 向量 | BM25 混合（术语密集文本） | 标题/章节加权（父块命中加分） |
| 论文库(0.3) | Dense 向量 | BM25（标题/摘要词） | 时间衰减加权（新论文加分） |

其他检索增强：
- **P1｜Query 改写/扩展**：医学术语同义词扩展（UMLS/中文医学词典），多症状复合查询分解成子查询。
- **P1｜HyDE**：LLM 先生成"假设答案"再用它检索（对病例库尤其有效）。
- **P1｜领域 Embedding**：换/微调 MedEmbed 或中文医疗 embedding，改善医学近义词区分。
- **P2｜图谱检索 1-hop → 多跳**：症状→疾病→药物→相互作用链路，或评估 MedGraphRAG。

### ③ 融合与排序（收益最大）
- **P0｜Cross-encoder 重排（Reranker）**：bi-encoder 粗召回 Top-K（20-30 条）→ bge-reranker 精排。只对 top-K 重排，成本低、收益立竿见影，是当前最缺的一层。
- **P1｜权重学习**：w=[0.8,0.6,0.3] 在评测集上网格搜索/贝叶斯优化，让权重由数据定。
- **P1｜自适应路由**：简单查询走单源/轻路径，复杂/疑难查询才走全源 + 重排，控制 P95≤2s。

### ④ 文档使用方式（注入与生成）
- **P1｜Contextual Retrieval**：chunk 附加上下文摘要再检索，提升命中（对应 2025 论文"信息可及≠可用"）。
- **P1｜引用溯源（Citation Grounding）**：每条结论标注"来自哪个 chunk + 证据等级 A/B/C"。
- **P2｜MMR 去重**：保证多源多样性。
- **P2｜冲突显式化**：论文与指南冲突时显式呈现，交给证据等级裁决，而非静默合并。

### ⑤ 评测闭环（先决条件）
- **P0｜建立检索评测集**：按 `医枢Agent.md` 21.5 节方案（100-200 条 query + golden labels），先跑出真实 Recall@10/MRR，再对每个优化项做 A/B test。
- **原则**：先建评测集，再谈优化，否则所有优化都是拍脑袋。

## 四、建议落地顺序（路线图）

| 阶段 | 任务 | 改动面 | 验证方式 |
|---|---|---|---|
| 1 | 修融合逻辑（选方案 A 或 B），图谱重构进融合 | `retriever.py` + `rag.py` | 156 回归 + 检索评测集 |
| 2 | 每库多路召回（先加理论库 BM25 混合、病例库症状词匹配） | `retriever.py` + `source.py` | RRF 源内融合开始真正生效 |
| 3 | Cross-encoder 重排 | 新增 reranker 模块 | Recall@10/MRR 对比 |

| 5 | 药品/处方知识库（第 4 路） | 数据入库 + source config | Review Agent 处方审查准确率 |
| 6 | Query 改写 / HyDE / 领域 embedding / 权重学习 / 自适应路由 | 检索链路逐步增强 | 逐项 A/B test |
